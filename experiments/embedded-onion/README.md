# App-owned embedded onion experiment

This separate, non-published Rust package pins the Tor Project's Arti 0.46.0 and composes it with the local cmsg core. Initial functions deliberately reject: the behavioral contract must first execute red on the existing hosted worker. No local build, test, dependency installation, host daemon or public-network result is claimed. A separate Cargo lock will be generated by the hosted worker and committed before interpreting an executed source revision.

The bounded experiment has two phases:

1. Tests use real Tor request types, owned private filesystem trees, cancellation/drop guards and actual cmsg MLS over bounded in-process streams. They verify allowed routes, virtual-port restrictions, refusal of unsafe storage locations, phase deadlines, capacity and cancellation. The in-process stream test is cryptographic/framing integration evidence, not a Tor network test.
2. An explicitly triggered network binary creates two synthetic app-owned Arti clients with separate state/cache trees, a generated v3 onion service and direct Arti data streams. It exchanges actual cmsg MLS ciphertext in both directions and checks the authenticated counterpart locally. It accepts ordinary `BEGIN` only on the configured virtual port, bounds rendezvous/stream acceptance instead of calling the upstream unbounded helper, and has no clearnet or proxy fallback.

The selected features are Tokio, Rustls, compression, onion client/service, vanguards and bundled SQLite. No generic experimental/full feature set, raw Tor implementation, external SMS/payment provider or real user credential is added. The test grant signer is the existing clearly synthetic `tests/common` fixture; this does not test cvld issuance or passive-reader anonymity.

All runtime paths are under a newly created private child of an explicitly supplied parent. Separate clients have distinct state and cache directories; Arti derives its keystore from each state location. Test identity keys may be written there by upstream Arti. A temporary directory and cleanup do not imply encrypted key storage or forensic erasure. Existing parent files must survive cleanup. App wallet wrapping and mobile lifecycle remain separate integration work.

The network phase uses fixed experiment bounds: at most 600 seconds for the owned run, separate bootstrap/publication/connection/acceptance/frame deadlines, bounded sequential rendezvous and stream attempts, and coarse phase/boolean output only. It must never print onion addresses, keys, profile text, message contents or participants. An address returned by the retained running service handle establishes which app-owned service was generated; reachability and an actual round trip are separate observations. Dropping that handle stops new introductions but upstream explicitly leaves established streams open, so all request streams and active tasks must also be owned by the cancellable run.

The cmsg codec treats a cancelled operation as terminal. Use sequential request/response operations or separate directional streams; never cancel a read with `select!` and reuse that codec for a later write. On observed disappearance, stop new acceptance and enqueueing, including after awaits. Already queued or received bytes cannot be retracted.

For profiles, direct native streams must preserve cfrm's exact `hello`/`challenge`/`read`/`profile` JSON envelopes, bounded UTF-8 bytes and full transcript nonce. Authenticate the stable owner, route, live session and signature before holder proof generation. A passive reader sends no member certificate, stable reader ID, cookie or central lookup. The existing Node socket adapter requires a real `net.Socket` and loopback forwarding; a direct native stream is a separate application adapter, not a fabricated successful loopback verifier.

Source basis: the checked [arti-client 0.46.0 archive](https://crates.io/api/v1/crates/arti-client/0.46.0/download) and [tor-hsservice 0.46.0 archive](https://crates.io/api/v1/crates/tor-hsservice/0.46.0/download), recorded in [the feasibility study](../../studies/embedded-onion-feasibility.md). The upstream Tokio feature provides the stream traits used by cmsg; writes require flushing. [Tor's incoming request type](https://docs.rs/tor-proto/0.46.0/tor_proto/stream/enum.IncomingStreamRequest.html) and [BEGIN API](https://docs.rs/tor-cell/0.46.0/tor_cell/relaycell/msg/struct.Begin.html) define the virtual-port boundary.
