# App-owned embedded onion experiment

This separate, non-published Rust package pins the Tor Project's Arti 0.46.0 and composes it with the local cmsg core. The explicitly triggered [Crow pipeline 31](https://crow.corbet.ch/repos/10/pipeline/31), at `fcc146755bbd574a4470861acdd96fc7c9633fc3`, **completed a real public-Tor MLS round trip**. TLS setup, both clients' bootstrap, generated endpoint ownership, onion publication, connection/acceptance, encrypted round trip and completion all passed. Two app-owned clients with separate state trees ran on the same CI worker and used direct Arti streams through the public Tor network. The member grants were synthetic fixtures.

This is functional transport evidence from that runtime. It does not establish resistance to traffic correlation, an audited anonymity system, native mobile behavior, encrypted production onion-key storage, real external eligibility or the complete counter protocol. The run did not exercise the cfrm anonymous-profile wire service or cvld credential issuance.

Before that network run, [pipeline 28](https://crow.corbet.ch/repos/10/pipeline/28) passed **all 11 integration contracts and the binary panic subprocess regression**, plus its inactive child helper, formatting and all-target compilation at `f5bc95031e666fb1d57215b163c2866a5fb19a58`. Those local checks establish runtime and cryptographic/framing behavior, including explicit TLS startup and panic redaction.

Earlier, [pipeline 22](https://crow.corbet.ch/repos/10/pipeline/22) passed the original 10 contracts at `34ab6226999f5871208b0f24f23e10ae3b33e2aa`. [Pipeline 19](https://crow.corbet.ch/repos/10/pipeline/19) had executed their initial contract at `ed9691bd6d3b422304946a565f0591955b6b0061`: nine tests failed against explicit implementation stubs, and one purely negative unsafe-parent test passed. That negative result alone established no storage safety.

The earlier public-network [pipeline 24](https://crow.corbet.ch/repos/10/pipeline/24), at `bc823ade38e83f38e32b2ffd010fbea2a9775789`, compiled successfully but failed immediately in bootstrap because Rustls could not select a process crypto provider. That revision's lock contained neither built-in backend as a dependency of Rustls itself; `ring` was present only through WebPKI. That failed runtime prerequisite established no successful onion connection or round trip. A new startup contract requires explicit, concurrent-safe, repeatable provider initialization followed by construction of a real TLS client without network access. [Pipeline 25](https://crow.corbet.ch/repos/10/pipeline/25), at `6c61bdb42310ca7f1f105774547c5a7c77da1818`, executed that regression: the prior 10 tests passed and the initializer test failed against its stub. The correction passed in pipeline 28 before the separate successful network run in pipeline 31.

The worker generated the separate 600-package lock in [pipeline 16](https://crow.corbet.ch/repos/10/pipeline/16), initially with SHA256 `4d7f92f3d527fa795378a3e4e4335ef05fc822f316ea6110fbba02a1d7193aed`. Later direct edges use already locked `safelog` 0.9.1 for upstream's explicit in-memory onion-address conversion and Rustls 0.23.44 for the startup regression, without changing resolved package versions. Compile prerequisite failures, including the stub entrypoint typo and two version-specific API corrections, are not behavioral results. No local build, test, dependency installation or host daemon was used.

The TLS correction explicitly enables Rustls's existing `ring` backend and installs its unchanged default provider before Arti or runtime initialization. A process-local `OnceLock` makes repeat/concurrent calls consistent; an unrelated provider installed earlier is refused. The lock adds the Rustls-to-`ring` edge using already locked `ring` 0.17.14. [Rustls documents early application-level provider selection](https://docs.rs/rustls/latest/rustls/crypto/struct.CryptoProvider.html). The checked [Rustls 0.23.44 archive](https://crates.io/api/v1/crates/rustls/0.23.44/download), SHA256 `6725596c3f2c3a0aef021139e145d4eafe314a6623e4680ca83852b2c67ab2ba`, confirms that its optional `ring` feature enables both the backend and WebPKI support. No custom cipher implementation or certificate verification policy is added.

The failed network run also exposed a diagnostic gap: Rust's default panic hook bypasses the coarse phase emitter. A separate binary subprocess regression injects a fixed synthetic panic payload and requires its absence from stdout and stderr while retaining a coarse failure event. [Pipeline 27](https://crow.corbet.ch/repos/10/pipeline/27), at `1f30849395ebe2b70c991fc85628c2a8b1dd9576`, executed its genuine red: the inactive child helper passed, but the subprocess parent failed because stderr contained the marker. That run stopped before the 11 integration tests; those are not additional results. The child probe exists only under `cfg(test)`. The binary now installs a hook before other initialization that discards the panic payload and emits only the coarse panic failure event; the subprocess regression passed in pipeline 28.

The bounded experiment has two phases:

1. Tests use real Tor request types, owned private filesystem trees, cancellation/drop guards and actual cmsg MLS over bounded in-process streams. They verify allowed routes, virtual-port restrictions, refusal of unsafe storage locations, phase deadlines, capacity and cancellation. The in-process stream test is cryptographic/framing integration evidence, not a Tor network test.
2. An explicitly triggered network binary creates two synthetic app-owned Arti clients with separate state/cache trees, a generated v3 onion service and direct Arti data streams. It exchanges actual cmsg MLS ciphertext in both directions and checks the authenticated counterpart locally. It accepts ordinary `BEGIN` only on the configured virtual port, bounds rendezvous/stream acceptance instead of calling the upstream unbounded helper, and has no clearnet or proxy fallback.

The selected features are Tokio, Rustls, compression, onion client/service, vanguards and bundled SQLite. No generic experimental/full feature set, raw Tor implementation, external SMS/payment provider or real user credential is added. The test grant signer is the existing clearly synthetic `tests/common` fixture; this does not test cvld issuance or passive-reader anonymity.

All runtime paths are under a newly created private child of an explicitly supplied parent. Separate clients have distinct state and cache directories; Arti derives its keystore from each state location. Test identity keys may be written there by upstream Arti. A temporary directory and cleanup do not imply encrypted key storage or forensic erasure. Existing parent files must survive cleanup. Runtime shutdown is bounded and cannot prove all upstream blocking tasks stopped. The hosted runner reaps the experiment process before removing its disposable outer parent; cleanup inside the binary is best effort. App wallet wrapping and mobile lifecycle remain separate integration work.

The network phase uses fixed experiment bounds: 600 seconds for the owned run, 180 each for bootstrap/publication, 60 for connection/acceptance, 30 per frame, and 120 for the active exchange scope. At most four sequential rendezvous attempts and four stream requests per accepted rendezvous are processed; the service permits one concurrent stream per circuit. Output contains only coarse phase/state results. It must never print onion addresses, keys, profile text, message contents or participants. An address returned by the retained running service handle establishes which app-owned service was generated; reachability and an actual round trip are separate observations. Dropping that handle stops new introductions but upstream explicitly leaves established streams open, so all request streams and active tasks must also be owned by the cancellable run. In particular, retain the accepted rendezvous request iterator through the exchange because it owns the tunnel's lifetime.

The cmsg codec treats a cancelled operation as terminal. Use sequential request/response operations or separate directional streams; never cancel a read with `select!` and reuse that codec for a later write. On observed disappearance, stop new acceptance and enqueueing, including after awaits. Already queued or received bytes cannot be retracted.

For profiles, direct native streams must preserve cfrm's exact `hello`/`challenge`/`read`/`profile` JSON envelopes, bounded UTF-8 bytes and full transcript nonce. Authenticate the stable owner, route, live session and signature before holder proof generation. A passive reader sends no member certificate, stable reader ID, cookie or central lookup. The existing Node socket adapter requires a real `net.Socket` and loopback forwarding; a direct native stream is a separate application adapter, not a fabricated successful loopback verifier.

Source basis: the checked [arti-client 0.46.0 archive](https://crates.io/api/v1/crates/arti-client/0.46.0/download) and [tor-hsservice 0.46.0 archive](https://crates.io/api/v1/crates/tor-hsservice/0.46.0/download), recorded in [the feasibility study](../../studies/embedded-onion-feasibility.md). The upstream Tokio feature provides the stream traits used by cmsg; writes require flushing. [Tor's incoming request type](https://docs.rs/tor-proto/0.46.0/tor_proto/stream/enum.IncomingStreamRequest.html) and [BEGIN API](https://docs.rs/tor-cell/0.46.0/tor_cell/relaycell/msg/struct.Begin.html) define the virtual-port boundary.
