# First-contact release after private receive accounting

**Design review, not an implemented or selected protocol.** The current cfrm [directional receipt hypothesis](https://github.com/corbet-labs/cfrm/blob/main/studies/directional-blind-receipts.md) leaves receive redemption voluntary. A modified client can omit it. An honest inviter could instead withhold the material needed to read its first private content until it sees a signed, recipient-bound proof that a receive debit was recorded. This is a possible way to enforce accounting at content release without submitting the participant pair to cfrm. It does not prove delivery, reading, sincere interaction or an atomic fair exchange.

## The current boundary does not enforce this

[`Inbox::accept`](../src/inbox.rs) receives the complete MLS Welcome, prepares and authenticates the join, and then asks an anonymous cfrm callback to redeem a first-contact permit for an unknown inviter. Its encrypted pending state holds the Welcome and permit retry claim. Only its final local commit makes acceptance visible in the compliant application.

A modified recipient already possessing a Welcome and first ciphertext can use the lower-level [`Member::join`](../src/member.rs) and omit Inbox or receive bookkeeping. Moving another callback inside `Inbox::accept` cannot prevent that. The sender must retain sufficient material to prevent decryption. For a fresh invitation it can retain both Welcome and first ciphertext until the gate completes. Releasing text, a usable Welcome plus available ciphertext, or an equivalent decryption secret earlier defeats the intended condition.

This also creates a consent ordering requirement: before incurring a receive debit, a recipient needs independently authenticated inviter metadata that it can inspect and block locally. The existing decrypted-Welcome verification cannot supply that preflight step while the Welcome remains withheld.

## Candidate exchange

Use the same certified community member IDs and keys already used by the forum and messages. All peer exchanges use authenticated, anonymous transport; this proposal adds no direct connection, operator relay or URL fetch.

1. **Authenticated private preflight.** Inviter `S` prepares the invitation and a fresh unpredictable release nonce, and durably stores an encrypted pending record binding that nonce to the intended `R`, its certified key, community/policy, expiry and the exact withheld material. A new fixed-purpose signature authenticates these private preflight fields. The recipient verifies current admission and key possession, applies its local block/consent rules and chooses whether to proceed. The preflight can commit to the encrypted Welcome; it cannot replace validating the Welcome itself after release. No plaintext digest is needed.
2. **Blind preparation.** `R` prepares and durably stores a receipt request containing its own certified account binding, the private release nonce and the common community/type/issuance-cohort context inside the blinded payload. `S` authorizes the request hash using the proposed separate sender-debit authorization. The public authorization nonce and private release nonce must be independent. Neither the release nonce nor an identifiable derivative, recipient ID, preflight signature, invitation digest or conversation identifier enters the named-sender operator request.
3. **Record the sender authorization.** The anonymous acknowledgement transaction commits `S.authorizedSend` and the cached blind response under the proposed cfrm rules. Before release, `S` must verify this transaction committed, for example through a separately domain-separated operator signature over its authorization nonce and request hash, or an authenticated lookup of its own committed authorization. That result must contain no recipient binding or private release nonce. Possessing `S`'s original debit authorization alone proves permission, not commit.
4. **Record the receive debit.** `R` unblinds and redeems with current admission and a receipt-specific certified-key authorization. The operator atomically consumes the receipt serial and increments the recipient's counter in the receipt's issuance cohort. It returns a separately domain-separated signed redemption attestation only for the committed result. Retries must recover the same result without another debit. Required fields bind the exact role, community/policy, trusted common attestation key, issuance cohort, recipient ID and certified key, private release nonce, and common expiry. No sender ID, sender authorization nonce, blinded request hash, proof nullifier or conversation ID appears in this result or redemption.
5. **Release once to the expected recipient.** `R` gives the attestation to `S` privately. `S` verifies the trusted operator signature and every binding against its encrypted pending record, including the freshly chosen nonce, expected `R` and key, cohort and expiry. Only then does it release the withheld invitation and first content. The recipient runs the real Welcome checks and existing first-contact permit path. Repeating a valid release should recover the same pending delivery, not authorize unrelated material or new invitations. Durable encrypted sender state must prevent nonce reuse across restarts and concurrent writers.

These are separate signatures with fixed canonical domains, not a generic signing oracle. The current cmsg public API has narrow rendezvous/profile signatures and no private-key export; it does not yet provide the new preflight, debit or redemption signatures. Blind-RSA issuance keys and redemption-attestation signing keys have different purposes. Attestation keys are shared across a sufficiently large cohort, not personalized per account or invitation.

The independently recorded sender and receiver results do not prove that the redeemed receipt came from that sender's particular blind signing interaction. Blindness removes that link. For the proposed release condition, the useful fact is that both required counters committed and that the receive attestation authorizes this one honest sender's fresh release challenge. Claims of same-pair reciprocity or receipt provenance remain unsupported.

## What this would and would not prevent

| Behavior | Conditional result |
|---|---|
| Modified `R` skips receive redemption | It cannot obtain the required signed attestation for its fresh release nonce, so an honest `S` withholds first content. This differs from a recipient-only UI check. |
| `R` replays an earlier attestation | Its nonce does not match a new honest sender's pending challenge. Same-delivery retries must return only the same already authorized material. |
| `R` supplies another account's attestation | The recipient ID and certified key do not match the intended counterpart. Sharing private credentials defeats identity separation, as elsewhere in the system. |
| Malicious prover initially designates a different hidden receipt owner | It may obtain a receipt for that owner, as the current circuit permits. Its resulting attestation cannot unlock honest content intended for a different `R`. Pooling remains possible in the accounting experiment; this release check does not prove hidden prover ownership. |
| `R` obtains the matching attestation through a different sender's authorization | It still needs an actual debit for its own account and the fresh release nonce. `S` separately requires its own authorized-send commit. This does not establish which issuance produced the redeemed receipt. |
| `S` disappears or sends invalid material after both counters commit | `R` can lose the debit without receiving useful text. There is no delivery proof, automatic refund, complaint or adjudication. The preflight consent and signed material commitment reduce ambiguity for the client but do not force delivery. |
| `R` completes redemption and discards the released material | It was counted before release, without proving receipt, decryption or reading. The counter must retain that exact meaning. |
| `S` and `R` cooperate to bypass the gate | They can exchange keys or text directly. The guarantee concerns content withheld by an honest participant; accepted collusion and external communication remain outside it. |

An unsolicited preflight causes no debit: the recipient must authorize its own redemption. A malicious inviter can nevertheless obtain consent and then withhold useful output. This fairness cost is a material functional tradeoff, not a minor recovery bug. Exact delivery-based accounting is still not established.

## Replies, groups and state

Only a new first-contact introduction uses the existing permit. An honest first reply may run the proposed reversed directional acknowledgement without another first-contact permit. Ordinary text in an established MLS conversation must not acquire a per-message debit. `Inbox` currently remembers accepted inviters locally; it does not automatically mark outbound invitees as known. The host must distinguish these cases through encrypted contact/pending state, rather than telling cfrm the counterpart IDs.

For a group with around 100 members, each newly admitted recipient needs its own release nonce, account-bound attestation and first-contact gate when its inviter is unknown. One attestation cannot unlock 99 independently challenged introductions. The new member's Welcome must remain unavailable until that member's gate completes. Other group members may already process an MLS commit and continue talking; coordinating pending membership with delivery therefore needs explicit lifecycle tests. A cooperating group member can share sufficient group key material or an available Welcome and defeat the gate, consistent with the honest-inviter boundary. Joining establishes contact with the authenticated inviter, not reciprocal activity with every member. This proposal must not debit every group sender or every group message.

Current Inbox checkpoints do not persist blind preparation, these attestations, sender release records or a combined retry state machine. Their existing final-commit behavior is necessary but insufficient. Neither authentic old-snapshot rejection nor multiple-device coordination is provided by the current alpha; replay-resistant release state needs the same unresolved monotonic storage work.

## Privacy and required evidence

The private release nonce is revealed to the operator only with the named receiver redemption. If it, its hash, an invitation digest, or its preflight signature is also included in the named sender phase, it becomes a deterministic join key. The operator-issued sender acknowledgement must not later accompany receiver redemption. Separate anonymous connections and common contexts remain necessary; timing and small cohorts can still correlate phases even when schemas contain no pair join. This proposal adds no proof against traffic analysis.

No implementation or runtime tests exist for this exchange. A meaningful experiment must prove with actual MLS material that a modified recipient lacks the withheld decryption input before a valid attestation, succeeds after it, and cannot substitute recipient, nonce, purpose, cohort or expiry. It must exercise lost responses, crash/restart retries, stale state, the initial permit boundary, no ordinary-reply charge, rejected preflight with no debit, dishonest withholding after debit, and separate challenges for group recipients. The operator's actual requests and retained records must be inspected for shared join fields. Those tests would validate the proposed conditional release rule, not truthful reading or global network anonymity.
